## 一、IDP个人能力发展目标

### 个人优势

1. **深厚的技术积累**：入司11年，深耕链路层领域，熟悉无中心、分层分簇、空分复用等核心技术方向，具备较强的技术判断力和方案把关能力
2. **全局视野与系统思维**：深度参与产品从立项到交付的全链路，对产品背景、系统总体架构及上下游协作模块有深入理解，能跨模块把握大局、识别关键路径，在多特性并行交付中有效规避系统性风险
3. **丰富的项目交付经验**：经历多个民品系列项目完整周期，对研发流程、集成风险、进度管控有深刻实战认知
4. **团队信任基础好**：在团队中有较高技术威望，骨干成员认可度高，具备带动团队的基础

### 个人不足

1. **管理经验尚浅**：从技术骨干向团队负责人转型初期，在任务分解、人员激励、差异化管理方式上仍需系统学习
2. **梯队建设意识待强化**：过去更多依赖个人技术能力兜底，对成员差异化培养的系统性方法论掌握不足
3. **向上沟通主动性有待提升**：面对需求不清晰、资源不足等情况，主动向上对齐的意识和技巧需加强
4. **机制建设经验不足**：团队行为准则、AB角机制、质量管控流程等从0到1建立的实践经验欠缺

### 四项能力发展目标

**① 任务管理与会议驱动能力**
- 目标：建立任务看板机制，做到定人定事定时间；团队形成主动汇报、风险上报习惯
- 计划：建立周报/站会规范 → 宣贯链路层行为准则 → 推行走动管理，持续至10月底

**② 梯队培养与AB角机制建设**
- 目标：AB角机制落地运行；泰利、符兵个性化培养计划执行，湘湘、任霜负责赋能带教
- 计划：明确分组与带教要求 → 泰利小模块实践 → 符兵备份任霜缺位 → 因人施策，按季度评估

**③ 质量管控与内部平台（CBB/自测试）建设**
- 目标：推动模块化重构与CBB建设；建立需规→设计→代码→自测试全流程闭环
- 计划：规范全流程文档 → 制定重构路线图 → 建立集成节点检查机制

**④ 基层管理思维与领导力系统提升**
- 目标：建立完整管理知识体系，掌握指令/教练/支持/授权四种领导方式
- 计划：整理培训内容输出管理手册 → 阅读管理书籍并应用 → 每月1对1沟通 → 结业汇报总结

## 二、梯队培养与AB角机制落地

### AB角分组

| 方向 | A角 | B角 | 核心目标 |
|---|---|---|---|
| 链路层组网 | 湘湘 | 泰利 | 泰利独立承接小模块 |
| 链路层资源 | 任霜 | 符兵 | 符兵备份任霜产假缺位 |

**A角职责**：负责带教和把关B角输出，降低项目风险
**B角职责**：承接真实工作，分担A角琐碎事务

### 落地四步

**第一步：定框架（第1周）**

开小会，把分组和逻辑讲清楚。强调：A角不是"甩任务"，B角不是"打杂"，否则容易变成A角不愿带、B角觉得被利用。

**第二步：定具体要求（第1-2周）**

| | 湘湘带泰利 | 任霜带符兵 |
|---|---|---|
| 教什么 | 组网方向模块设计、任务拆解方法 | 资源方向业务逻辑、开发规范 |
| 怎么教 | 任务拆解时拉上泰利讨论，给泰利分配小模块独立承接 | 符兵跟做小功能，任霜代码评审+讲解 |
| 怎么验收 | 泰利输出湘湘把关后提交，你抽查 | 符兵功能交付任霜签字确认质量 |

**第三步：差异化启动（因人而异）**

- **湘湘**：单独谈，给"骨干带动"的定位感，让她感受到信任和成长机会，而不是额外负担
- **任霜**：强调"符兵是来帮你分担的"，9月产假前把东西交出去，她能放心休假，把AB角包装成对她有利的事
- **泰利**：指令式启动，先给明确小任务，不让他自己摸索，做完给正向反馈，逐步建立信心
- **符兵**：明确告诉他跟任霜学什么、学到什么程度，给清晰成长路径

**第四步：建检查节点**

- 每两周：走动管理时顺带问带教进展，不用开专项会
- 每月：周会上让A角简单汇报B角进展和问题
- 里程碑节点：泰利独立完成第一个模块、符兵独立承接第一个功能，明确庆祝，强化正向信号

### 常见坑：A角不愿带

A角往往觉得"自己做更快"。需要在考核/认可上体现带教价值，让湘湘和任霜感受到"带好B角"是她们工作成果的一部分，而不是额外负担。

## 三、架构设计与CBB：没有时间推进怎么办

### 根本矛盾

架构设计和CBB属于**重要不紧急**的事，在五重职责全压、天天有紧急事项的情况下，永远被挤掉。这是结构性问题，不是努力程度的问题。

**当前时间被吃掉的三类事（4-5月工作记录）：**
- 救火类：外场问题、CRC问题、TCP优化、MAC频繁挂死定位
- 评审类：需求评审、方案评审、总体设计讨论（5月1320累计16天）
- 协调类：与其他科室拉通、接口对齐、组内置顶

### 三个解法同时做

**① 向上理清职责边界**

和上级明确提出：
- 日常进度跟进 → 让湘湘承担，你只做关键节点介入
- 质量把关 → 建立AB角机制后，从逐条评审变成抽查
- 早会主持 → 强制轮值，你不再兜底

**② 给架构时间划硬保护**

- 每周固定2个半天（如周二上午、周四上午）作为架构时间
- 这两个时间段不排评审、不接临时需求
- 在团队公开宣布，作为制度而非个人习惯（制度不会被打破，习惯会）
- 紧急问题定义：当天不处理会导致项目停摆，否则下午再说

**③ CBB建设颗粒化，交出去做**

CBB推不动的另一个原因：这件事在你脑子里，没有被拆解成别人能接手的颗粒度。

- 花一个架构时间，把CBB建设拆成5-10个独立模块
- 把不需要你亲自做的模块交给湘湘或任霜承接
- 你只负责定方向、评审输出，不亲自写

### 链路层行为准则（配套）

1. **工作汇报 + 风险上报**：主动上报，不等被问
2. **KB方案记录 + 自测试**：过程留档，不只交结果
3. **评审记录 + 闭环**：评审意见有跟踪，问题有闭环

## 四、是否转系统室做纯粹的系统工程师

### 先把真正的问题说清楚

考虑转岗，背后可能有几个不同的驱动：

| 可能的驱动 | 本质 | 转岗能解决吗 |
|---|---|---|
| 五重职责压得喘不过气 | 负荷问题 | 不能，换了地方一样 |
| 职责边界不清 | 组织结构问题 | 不能，可以在现岗解决 |
| 想做系统设计，不想做管理和交付 | 职业方向问题 | 能，这才是真正的转岗理由 |
| 在链路层做架构没有空间 | 发展天花板问题 | 部分能 |

### 转过去的得与失

**得到的：**
- 职责单一，从需求包开始介入，做真正的系统设计
- 从"被需求驱动"变成"驱动需求"，更接近上游
- 11年链路层积累在系统室有差异化竞争力

**失去的：**
- 11年建立的技术权威和团队信任，到系统室要重新建立
- 系统工程师的工作重心是需求澄清、方案拉通、接口对齐，**会议和协调类工作不会减少，甚至更多**
- SE和SE组成员边界依然模糊，可能更困惑

### 建议

**短期（3个月内）：不要急着决定。** 先把架构时间保护住、CBB颗粒化交出去做。如果做完之后对链路层的工作依然提不起兴趣，那才是真正的方向信号。

**中期（6个月）：观察自己做架构设计时的状态。** 如果有能量，说明你需要的是空间，不是转岗；如果更享受系统级的需求拆解，那转系统室值得认真推。

**无论转不转，都要做的一件事：** 和上级摊开谈职责边界——"链路层负责人这个角色，哪些职责是核心的，哪些是临时压上来的？"这个对话本身会帮你看清楚现在是结构性问题还是方向性问题。

## 五、单点依赖陷阱与副主任角色应对

### 单点依赖的本质

所有人把你当"万能接口"——需求不清找你，争论找你，协调找你，早会没人开找你。这不是因为他们懒，而是**找你是最低成本、最高成功率的路径**，这个模式已经固化。

### 应对副主任升职的三件事

**第一件：谈条件，不是谈待遇**

升职前和上级明确副主任职责边界，白纸黑字确认：

在职责范围内：
- 技术方向把关：架构决策、CBB规划、重大方案评审
- 团队能力建设：梯队培养、AB角机制、技术规范制定
- 向上接口：代表团队参与跨部门重大技术决策

不在职责范围内：
- 日常需求拉通和协调（主任设计师职责）
- 具体模块开发和问题定位（工程师职责）
- 早会主持和日常进度跟踪（轮值/项目负责人职责）

**第二件：打破单点依赖，让依赖变得"有成本"**

| 问题 | 当前模式 | 改变方式 |
|---|---|---|
| 早会无人主持 | 你兜底 | 建强制轮值表，没人主持就取消 |
| 需求不清 | 你去搞清楚 | 提出方整理问题清单，你只做最终裁定 |
| 对外battle | 你替他们打 | 带当事人去，你旁观，他们先表达 |
| 组网方向事务 | 你确认 | 「这个找湘湘」，说完不解释不补充 |

**第三件：给技术工作划硬时间（制度化，不是个人习惯）**

在团队层面公开宣布：
> 「每周二、周四上午是架构研究时间，这两个时间段日常事务走AB角，不找我。紧急问题的定义是：当天不处理会导致项目停摆，否则下午再说。」

### 任命不需要等到7月10日

**不需要等，现在就可以开始改变行为方式。**

任命前开始转变，别人看到的是"他在培养湘湘独立承担"；任命后才变，别人会觉得"他升职了所以甩手"。等任命下来，新角色已经自然过渡，不需要宣布，不需要解释。

**今天就可以做的一件事：** 下次有人来找你确认组网方向的事，你说：「这个问湘湘，她最清楚。」就这一句，今天开始。

### 转交湘湘的具体动作

找湘湘单独谈15分钟，说清楚三点：
1. 任命7月10日下来，组网方向的日常拉通协调以后由她主导
2. 遇到搞不定的你压阵，但她先上
3. 从下周早会开始，组网方向的事她来跟

之后，凡有人来找你确认组网方向的事，只说一句：「这个找湘湘，她负责组网方向。」重复三次，习惯建立。

## 六、需求不清的正确处理方式

### 根本原则

需求不清时，你的职责是**把选项和代价摆清楚，逼决策者做决策**，而不是替他们找答案。你不是来替他们做决定的，你是来帮他们看清楚决定代价的。

### 向上：TCP业务 vs TDMA 5ms体制冲突

产品经理不清楚需求、系统总体不愿意改体制，这个烂摊子被转移到你身上了——这是角色错位。

**正确做法：书面输出三条路，设截止时间。**

```
当前约束：TDMA 5ms体制，TCP业务在此体制下存在X问题（写具体数据）

选项：
- 方案A：需求侧降级，TCP业务接受≥Xms时延，不改体制，链路层可实现
- 方案B：体制侧调整，帧结构改为Yms，链路层改动范围Z，系统总体需评估影响
- 方案C：本期不支持TCP业务，需求延后或砍掉

→ 需要产品经理和系统总体在本周五前给出选择，否则按方案C处理。
```

设deadline，超时按最保守方案执行。不等不催，让不决策的代价落到该负责的人身上。

### 向下：员工说"你给我需求"

**先判断员工类型：**

- **第一种：真的不知道**（能力问题）→ 教练式带教，带他推导，不直接给答案
- **第二种：知道但不想担责**（态度问题）→ 逼他说出自己的判断，再让他提方案你审

**针对第一种，给分析框架让他自己填（以TCP为例）：**

```
1. 时延约束：帧周期5ms，RTT最短是多少？TCP超时重传门限是多少？
   → 由此推导最大可接受跳数

2. 带宽约束：给TCP业务分配多少时隙？满足基本TCP吞吐需要多少？
   → 和现有业务怎么共存

3. 可靠性约束：无线链路误包率X%时，TCP吞吐会下降到多少？
   → 是否需要链路层重传配合

结论：在不改体制的情况下，TCP能支持的场景是___，不能支持的是___。
```

让他填数，填的过程就是搞清楚需求边界的过程。

**针对第二种，正面点破：**
> 「你做了多久链路层？这个你真的没有判断？」

逼他说出判断之后：「好，你这个判断我认可，你按这个方向先做方案，做完我来把关。」

**流程改变：**
- 旧模式：需求不清 → 你去搞清楚 → 你告诉他 → 他去做
- 新模式：需求不清 → 他先分析技术约束 → 他提出可行范围 → 你确认 → 他去做

## 七、团队人员分工与关键风险预案

### 当前团队构成与分工

| 成员 | 情况 | 负责方向 | 领导方式 |
|---|---|---|---|
| 湘湘 | 毕业3-4年，技术骨干 | 组网方向A角 + 接手日常拉通协调 | 授权式 |
| 任霜 | 29周孕期，约9月中离岗 | 资源方向A角 | 支持式+认可 |
| 泰利 | 36岁，能力待提升 | 组网方向B角 | 指令式→教练式 |
| 符兵 | 毕业1年，已学自适应 | 资源方向B角（资源管理待学） | 教练式 |
| 新员工 | 7月入职 | 跟任霜学资源管理 → 后期接手数据模块日常维护 | 指令式 |
| 你 | 副主任 | 数据处理方向 + 总体架构设计 | — |

### 任霜的专项应对

任霜说话冲，本质是：需求一直在变，感觉被动应付，用硬话来防御。

**当下接话方式（不正面争对错）：**
> 「你说得对，需求确实没说清楚，所以我才拉这个群，咱们一起把边界摸清楚。你作为特性负责人，你最了解一条链路的情况，这个群里你的判断最重要。」

把她从"被批评的人"变成"最懂这件事的人"。

**长期改变主动性：**
1. 给她清晰的边界，边界内的事她有决策权，不用每件事等你点头
2. 她主动做了事，群里当众认可——「这个任霜已经跟进了」一句话就够

### 关键风险一：任霜缺位（高优先级，时间确定）

**现状**：任霜29周，约9月中旬离岗；新员工7月入职，扣培训后实际学习窗口只有6-8周，**无法完全接手资源管理，这是事实。**

**立刻执行——任霜开始输出文档：**
- 每周固定输出资源管理核心知识、常见问题处理、当前版本的坑
- 不要求完整，要求能用
- 话术：「你的文档是团队资产，你休假前把这些留下来，也是对自己工作的交代。」

**任霜离岗后的分层预案：**

| 优先级 | 工作内容 | 谁来做 |
|---|---|---|
| 一类（必须保障） | 线上紧急问题定位、版本发布关键验证 | 你兜底，或湘湘临时覆盖 |
| 二类（新员工跟做） | 常规维护、非紧急问题跟进 | 新员工做，你或湘湘把关 |
| 三类（可延后） | 新特性开发、优化类需求 | 向项目经理说明，提前延期 |

**现在就向上说（不要等到离岗才暴露）：**
> 「任霜29周，预计9月中离岗，资源管理方向存在缺位风险，新员工来不及完全接手，建议提前做好预案——要么调配人力支援，要么明确该方向任霜离岗期间的需求优先级。」

### 关键风险二：数据模块无B角

短期无法靠培养解决，分两步走：
1. **知识显性化**：模块架构、核心逻辑、历史踩坑、定位思路 → 文档化
2. **新员工稳定后**，承接数据模块日常维护（不要求能定位复杂问题，常规维护不用你亲自做即可）

复杂问题定位短期你仍需兜底，但目标从"脱不开身"变为"偶尔介入"。

### 风险上报原则

你一个人扛不住，也不应该一个人扛。把风险量化清楚，提出来，让上级做决策——是调人、是降需求、还是接受风险，这是上级该做的事。**风险你提了，就是管理到位；你不提，出了问题就是你的锅。**

## 八、角色转型：从技术骨干到副主任

### 核心转变

| 旧角色 | 新角色 |
|---|---|
| 最强执行者，亲自解决问题 | 团队放大器，让团队能解决问题 |
| 问题的终点 | 问题的路由器 |
| 靠个人技术能力兜底 | 靠规则、机制、人才培养兜底 |
| 绩效=我解决了多少问题 | 绩效=团队解决了多少问题 |

### 副主任绩效的三类输出

**第一类：技术决策**
- 重大方案的拍板、架构方向选择、跨模块技术取舍
- 输出形式：决策文档，留记录

**第二类：规则和标准**
- CBB规范、代码模块化标准、自测试体系、知识库沉淀要求
- 特点：做出来之后团队所有人受益，你走了依然存在

**第三类：团队能力**
- 湘湘能独立带方向、符兵能独立承接功能、新员工三个月能上手
- 要记录，述职时说得出来

### 述职话术示例

> **交付成果**：「我负责的方向，交付了X个特性，质量达标，进度可控——这是团队的成果，我负责保障。」

> **能力建设**：「湘湘从执行骨干成长为方向负责人，泰利完成了第一个独立模块交付，新员工三个月完成资源管理方向接手——这是团队能力建设的成果，我负责培养。」

> **平台建设**：「完成了CBB第一阶段建设，模块化重构启动，自测试体系建立——这是平台建设成果，我负责推动。」

### 核心转变

> 把「我能解决这个问题」的成就感，换成「他们能解决这个问题了」的成就感。这个转变完成了，时间自然就出来了，架构和技术的空间自然就有了。
